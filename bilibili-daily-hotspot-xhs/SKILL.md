# B站日报热点转小红书

使用这个 skill，把一个或多个 B 站日报类 UP 主的最新视频，转成有来源、有素材建议、可发布的新闻简报/早报内容批次。

工作流有两条硬边界：先采集和结构化事实，再只基于已核验来源写内容。

B 站视频、置顶评论和章节图只作为热点线索入口，不作为成稿里的事实来源或配图来源。生成发布稿时，不要写"B 站视频提到""视频信息卡显示""据 UP 主介绍"这类表述；正文必须改写为来自官方来源、论文、GitHub、产品文档、公司公告或可信媒体的事实表述。

## 反洗稿硬规则（写稿前必读）

**不要拿公众号文字版 / UP 主整理稿 / 其他媒体稿当内容素材洗稿。** 即便结构、措辞、要点看起来都对，正文也不能是它们的"改写版"。具体来说：

- 公众号 / UP 主文字版 / 同类早报稿只用来定位"是哪条热点、跳到哪个一手 URL"，不直接进正文。
- 每条成稿的事实、参数、链接、截图建议都必须来自该热点对应的**一手来源**——HF 模型卡、GitHub 仓库 / Release / Issue、arXiv 论文、产品页、官方博客、公司新闻稿、官方社交账号原文。
- 没有一手来源支撑的，不写进成稿；放进"需核实选题池"或直接放弃。
- 即便有官方一手来源，正文也只提炼**该来源里出现过的**事实点，不要把别的稿件里补的"上下文"混进来当事实。
- 配图一律从一手页面（HF / GitHub / 产品页 / 官方公告页 / arXiv / 公司新闻稿）抓，B 站视频截图、UP 主整理卡片、第三方早报截图一律不收。

## 快速开始

运行采集脚本：

```bash
python scripts/collect_bili_daily_hotspots.py --up <mid-or-space-url-or-name> --up <another-up>
```

如果用户直接给了视频链接或 BV 号，也可以直接采集指定视频：

```bash
python scripts/collect_bili_daily_hotspots.py --video <bvid-or-video-url>
```

可选输入：

```bash
python scripts/collect_bili_daily_hotspots.py --up-file up_list.txt --max-hotspots 20
```

环境变量：

- `BILIBILI_COOKIE`：可选登录 Cookie，用于增强 WBI、风控或受限访问稳定性。不要写入任何文件。
- `BILIBILI_USER_AGENT`：可选浏览器 UA 覆盖。

脚本返回 JSON，字段包括 `up_name`、`mid`、`video_title`、`bvid`、`aid`、`pubdate`、`video_url`、`pinned_comment`、`hotspots[]`、`warnings[]`。

**重要**：脚本依赖 B 站公开 API + WBI 签名，遇到风控、接口变更或 Cookie 失效时会失败。只要脚本没拿到有效数据（`results` 为空、某条 `error` 非空、或风控提示），就按下面的「API 失败兜底：chrome-devtools MCP」章节切换到浏览器采集，不要在 API 上反复重试或假装采集成功。

## API 失败兜底：chrome-devtools MCP

当采集脚本的 API 请求无效时（包括但不限于：HTTP 412 / -352 / -403 / -101 等风控错误、`could not initialize Bilibili WBI signing`、所有 `results[].error` 都非空、`results` 整体为空、或接口返回非预期结构），**停止重试 API**，改用 chrome-devtools MCP 通过真实浏览器拿数据。

### 前置依赖

chrome-devtools MCP 需要由宿主/客户端提供。本 skill 只负责调用它，不负责安装。配置参考（在宿主支持 MCP server 配置时）：

```json
{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": [
        "-y",
        "chrome-devtools-mcp@latest",
        "--browserUrl",
        "http://127.0.0.1:9222"
      ]
    }
  }
}
```

其中 `--browserUrl http://127.0.0.1:9222` 表示连接到本地已用 `--remote-debugging-port=9222` 启动的 Chrome/Edge；如果宿主用的是独立启动模式（不带 `--browserUrl`），按宿主默认即可。

### 判断 chrome-devtools 是否可用

- 先尝试调用任意一个 `mcp__chrome-devtools__*` 工具（例如 `list_pages`）。
- 如果工具不存在、调用直接报错、或返回未连接/未安装类的错误，就判定为**不可用**。

### 不可用时的处理（硬性要求）

只要判定为不可用，**立即停止采集并向用户报错**，不要静默降级到"猜数据"。报错必须包含以下信息：

1. 明确说明 API 采集失败、且 chrome-devtools MCP 兜底也不可用。
2. 给出可复制的 MCP server 配置（上面那段 JSON）。
3. 给出两条具体操作指引：
   - 在宿主/客户端里安装并启用 `chrome-devtools-mcp`（通常是 `npx chrome-devtools-mcp@latest`，或 `--browserUrl http://127.0.0.1:9222` 连接本地调试端口）。
   - 用调试端口启动 Chrome：`chrome.exe --remote-debugging-port=9222`（或对应平台的 Chrome/Edge 命令），再让 MCP 连接到该端口。
4. 提示用户：装好/启用 chrome-devtools MCP 后重新运行本 skill，即可走浏览器兜底路径完成采集。

报错模板（可直接套用）：

```text
B 站 API 采集失败，且 chrome-devtools MCP 兜底不可用，无法完成本次采集。

请先安装并启用 chrome-devtools MCP（本 skill 不自带该工具）。MCP server 配置：

{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": ["-y", "chrome-devtools-mcp@latest", "--browserUrl", "http://127.0.0.1:9222"]
    }
  }
}

操作步骤：
1. 用调试端口启动 Chrome：chrome.exe --remote-debugging-port=9222
2. 在宿主里按上面的 JSON 配置启用 chrome-devtools MCP。
3. 重新运行本 skill，API 失败时会自动切到浏览器兜底采集。
```

### 可用时的浏览器采集流程

确认 chrome-devtools 可用后，按以下顺序采集，**采集到的数据要和脚本输出保持同结构**（`up_name` / `mid` / `video_title` / `bvid` / `aid` / `pubdate` / `video_url` / `pinned_comment` / `hotspots[]` / `warnings[]`），方便后续核验与写作步骤无差别复用。

1. **定位 UP 主空间**
   - `mid` 形式：`navigate_page` 到 `https://space.bilibili.com/<mid>/video`。
   - 用户名/空间链接形式：同样导航到对应空间页，从页面里读出真实 `mid` 和 UP 名。
   - 用户名搜索不稳定时，按脚本同样的口径提示歧义。

2. **取最新视频**
   - 在空间投稿页直接读列表里第一条视频的标题、BV 号、链接。
   - BV 号从 URL `https://www.bilibili.com/video/<bvid>` 里正则提取。
   - `navigate_page` 到该视频页。

3. **取简介外链（主路径，优先）**
   - 在视频页用 `take_snapshot` 或 `evaluate_script` 读取视频简介（`desc`）全文。
   - 从简介里抽链接（公众号、Notion、独立博客等"文字版/相关链接"）。
   - `navigate_page` 到该链接，`take_snapshot` 抓正文，按 `parse_hotspots` 同口径解析 `00:09 ...`、`04:56 ...`、`1:02:33 ...` 时间轴行，保留原始行、时间戳、规范化标题、来源 UP、视频链接、来源类型。

4. **兜底：置顶时间轴评论**
   - 简介没有外链、外链打不开、或解析不出热点时，回到视频页评论区。
   - 展开并置顶评论优先（评论区顶部），读全文；没有置顶再用第一条高赞/根评论，`source_type` 记为 `fallback_high_like_reply`。
   - 同样按时间轴正则解析热点。

5. **直接给了视频链接/BV 号**
   - 跳过空间页，`navigate_page` 直接到该视频页，从第 3 步开始走。

### 浏览器采集的硬约束

- 浏览器拿到的是同一个"热点线索入口"，**不升级为成稿事实来源**：B 站简介、置顶评论、视频画面、章节关键帧仍然只能用来定位热点，正文事实必须来自一手来源核验（见「工作流」第 4 步和 `references/source-checking.md`）。
- 反洗稿硬规则在浏览器兜底路径下完全不变：公众号文字版/UP 主整理稿只用来定位一手 URL，不进正文。
- 不要把 B 站页面截图当作发布稿配图。



## 工作流

1. 采集每个 UP 主的最新视频。
   - 默认先用采集脚本（`scripts/collect_bili_daily_hotspots.py`）走 API；脚本失败/被风控时，按「API 失败兜底：chrome-devtools MCP」切到浏览器采集。
   - 未提到具体 UP 主则从 https://space.bilibili.com/285286947 的 UP 主列表里采集。
   - 优先使用数字 `mid` 或 `space.bilibili.com/<mid>`。
   - 允许输入用户名，但用户名搜索不如 `mid` 稳定；如果结果可能有歧义，要提示。
   - 如果 B 站返回风控或权限错误，提示用户配置 `BILIBILI_COOKIE`，不要假装采集成功；仍失败就进入 chrome-devtools MCP 兜底（不可用则按兜底章节的报错模板提示用户安装）。
   - 如果用户提供的是明确视频链接或 BV 号，直接用 `--video` 跳过 UP 最新视频接口；这通常比空间投稿接口更不容易触发风控。

2. **优先**从视频简介里拿到外链（这是主路径）。
   - 用 `/x/web-interface/view?bvid=<bvid>` 接口取 `desc` 字段。
   - 简介里的链接通常指向 UP 主整理的"文字版 / 相关链接"（公众号、Notion、独立博客等）。
   - 抓取该链接页面，从正文里逐条解析热点标题、要点和具体跳转 URL。
   - 解析形如 `00:09 NVIDIA ...`、`04:56 VoidZero ...`、`1:02:33 ...` 的时间戳行（如果该来源用时间轴的话）。
   - 保留原始行、时间戳、规范化标题、来源 UP、视频链接和**简介链接来源**（不是 B 站评论）。
   - 简介链接必须实际抓到正文；只看到标题不算。

3. **兜底**：如果简介里没有外链，或者外链页面打不开 / 抓取失败 / 解析不出热点，回退到 B 站置顶时间轴评论。
   - 优先使用 `data.upper.top` 里的评论。
   - 如果没有置顶评论，再回退到第一页高赞/根评论，并把 `source_type` 标记为 `fallback_high_like_reply`。
   - 解析形如 `00:09 NVIDIA ...`、`04:56 VoidZero ...`、`1:02:33 ...` 的时间轴行。
   - 保留原始行、时间戳、规范化标题、来源 UP、视频链接和评论来源类型。

4. 写作前先核验热点。
   - 简介链接或置顶评论里已经给了具体跳转 URL 的，直接抓取对应页面（HF / GitHub / 官方博客 / 论文 / arXiv / 公司公告 / Bloomberg 等），把每条热点对应的事实和原话记下来。
   - 简介链接或置顶评论里只给标题没给链接的，从热点标题中抽取中英文关键词检索。
   - 优先使用官方博客、产品文档、GitHub 仓库/Release/Issue、论文、公司公告和官方社交账号。
   - 可信媒体只在找不到一手来源或需要补充背景时使用。
   - B 站置顶评论、视频画面、章节关键帧、UP 主文字版只能用于发现热点，不能作为小红书正文中的事实依据。
   - 如果没有来源能确认核心事实，把它放进"需核实选题池"，不要当成确定事实写。
   - 更细的溯源规则见 `references/source-checking.md`。

5. 打开来源页，逐页检查图片和素材线索。
   - 不要只写"GitHub README / 项目页 / 论文首页"，必须打开页面并列出具体可用区块。
   - 优先找官方截图、产品页首屏、GitHub README 图表、论文架构图、项目页 Demo、Framework 架构图、benchmark 表格或模型页信息卡。
   - 不要把 B 站视频截图、章节关键帧、视频封面、UP 主整理卡片放进发布稿的"图片"区。它们最多只能作为内部线索或临时核对材料。
   - 不要把每篇限制为 1 张图；如果同一热点有架构图、参数表、Benchmark、Demo、产品界面、模型卡等多个高价值素材，可以在同一篇内容的"图片"区放多张。
   - 对每个素材写清楚 `页面 URL`、`区块名称`、`可截图内容`、`为什么适合配图`。
   - 默认不下载受版权限制的图片。记录 URL、可截图位置和使用备注。
   - 图片权属不明确时标注"需人工确认版权/授权"。

6. 生成新闻简报式内容。
   - 默认写成 AI 早报/科技新闻简报：标题 + 正文 + 标签 + 图片 + 相关链接。
   - 每条内容先给概括句，再补关键参数、能力、开放方式、适用场景和限制。
   - 发布稿正文不要引用 B 站作为事实来源，不要出现"B 站视频提到""视频里说""视频信息卡显示""UP 主称"等措辞。
   - 避免第一人称体验、情绪化种草、夸张标题、无依据排名、编造价格、编造用户反馈和绝对化结论。

## 必须输出

按下面结构输出：

```text
热点总览
- 简介链接状态 / 兜底来源 / 抽取热点

素材核验表
- 热点 / 事实来源 / 图片建议 / 可信度 / 风险

小红书内容
1. 热点：
   标题：
   正文：
   <标签行（去掉"标签"二字，直接跟标签，紧贴正文）>
   图片：
   相关链接：
```

**单篇格式细节**：
- 正文段落结束后，**直接换行写标签**，标签前不要再加"标签："或"标签"二字，方便一键复制。
- 标签格式：`#标签1 #标签2 #标签3 ...`，贴合单条热点，不使用 `#AI早报` 这类合集标签。
- 图片区可以是一张或多张图；多图优先选择彼此信息不重复的图表、架构图、数据表、功能截图和官方页面截图。
- 图片区禁止使用 B 站视频截图、视频封面、章节关键帧或 UP 主整理卡片；如果找不到合适图片，输出来源链接和手动截图建议，不要用 B 站图顶替。
- 相关链接优先放官方 / 一手页面（Hugging Face / GitHub / 官方博客 / arXiv / 官方公告 / 公司新闻稿等），可信媒体作为补充。

## 默认值和边界

- 平台：小红书或公众号，默认偏新闻简报/AI 早报写法。
- 口吻：客观、信息密集、少第一人称；KOC/轻测评仅在用户明确要求时启用。
- 批量数量：不做硬上限。简介链接 / 置顶评论里抽到多少条有效热点、且每条都能拿到一手来源并通过事实核验，就写多少篇，全部成稿。除非用户明确要求"只写 5 篇"之类的限制，不要自行截断。
- 小红书发布稿默认每个热点单独成篇，只输出标题、正文、标签、图片、相关链接。
- 标题优先体现完整热点信息，可以略超 20 字；不要为了短牺牲核心主体、产品名或动作。
- 不要使用 `#AI早报` 这类合集标签，标签要贴合单条热点。
- 不自动发布。
- 找不到来源时不编造事实。
- 不在 skill 目录里保存 Cookie 或私密 token。
